Abstract 
A construction worker may save a site update while the internet is unavailable. 
The application can keep that record locally and send it later, but a second problem 
appears when the server saves the record and its response never reaches the device. The 
client cannot tell whether the operation succeeded. Resending is necessary for reliability, 
yet it can repeat a payload that the server already holds. This proposal examines that 
narrow problem through the database and software engineering of offline -first 
applications. 
The study will specify and evaluate a receipt -aware retry algorithm. An entry and 
its pending operation will first be saved in one local transaction. The server will store the 
entry and a receipt in one database transaction, using a stable operation identifier to 
prevent duplicate inserts. Following an uncertain delivery, the proposed algorithm will 
request a small receipt before deciding whether to resend the full record. Its main 
comparator will use the same persistence and duplicate -prevention mechanisms but 
resend uncertain records directly. 
A focused narrative literature review will guide the design and identify its 
relationship to existing work. The prototype will use a progressive web application, 
IndexedDB, and a small relational server database. Synthetic construction site logs will 
provide a bounded workload motivated by the researcher's NBCC project context. 
Evaluation will measure correctness, transferred application bytes, request count, and 
completion time under four controlled scenarios. The expected contribution is a precise 
algorithm specification and evidence about its tradeoffs. The study will establish when 
receipt checking is useful rather than assume that it always improves synchronization. 
Keywords: offline-first applications; synchronization; retry algorithm; 
IndexedDB; idempotency; database transactions; software engineering.

CHAPTER 1: INTRODUCTION 
1.1 Background of the Study 
Work does not always stop when a connection fails. A site supervisor may still 
need to record completed work, describe an issue, or prepare a daily update. An 
application that saves only through a remote server makes these ordinary tasks depend on 
network availability. Offline -first software addresses this dependency by allowing the 
user to save locally and synchronize later. Local -first research places continued access to 
local data among its central design goals [1]. 
The browser provides useful building blocks for this approach. IndexedDB stores 
structured records through transactions, while a service worker can help an application 
reopen using cached assets [2], [3]. These capabilities address different parts of the 
problem. A cached interface makes the form available; a local database keeps the entries; 
a synchronization algorithm determines what happens when the application contacts the 
server. 
This research is motivated by my work on the management information system at 
mis.nishatbrothers.com for Nishat Brothers Construction Company (NBCC). The 
construction context provides a practical example of records that may need to be captured 
before they can be transmitted. The experiment will use an isolated prototype and 
synthetic site logs. It will not depend on access to company production data or assume 
that a particular synchronization mechanism already exists in the MIS. 
1.2 Problem Statement 
Consider an entry describing work completed at a site. The application sends it, 
the server commits it, and the connection fails before the acknowledgement returns. From 
the client's perspective, this looks similar to a request that never reached the server. 
Simply removing the entry from the queue risks losing work. Retrying with a new 
identity can create a duplicate. Retrying the same stable operation identity can avoid 
duplicate application, but still retransmits the full payload [4]. \nPAGE 7\n

The problem addressed here is how to recover from this uncertainty while 
preserving record integrity and controlling communication cost. The proposed algorithm 
checks for a committed server receipt before resending an uncertain operation. This may 
save bytes when the original request succeeded. It may also add an unnecessary request 
when it failed before commit. Both outcomes matter, particularly because site -log records 
can be small. 
1.3 Research Gap 
Transactional outboxes, idempotent processing, and selective synchronization 
already exist [4] –[6]. Their existence rules out a claim that stable identifiers or receipt 
checking alone are new inventions. The research opportunity is a focused design and 
comparison: under what failure conditions does receipt checking improve a browser 
application's retry behavior, and what does it cost when it does not? 
The study will examine this question for one append -only record type. It will 
contribute an explicit protocol, a reasoned statement of its properties, and a reproducible 
comparison with safe direct replay. The narrative review will refine the contribution 
before implementation. Claims of originality will be limited to differences that the review 
actually supports. 
1.4 Research Aim 
To design and evaluate a receipt -aware retry algorithm that preserves the integrity 
of offline-captured records and determines whether checking server receipts can reduce 
unnecessary retransmission after uncertain delivery. 
1.5 Research Objectives 
1.  Synthesize relevant literature on local persistence, idempotent requests, and recovery 
from uncertain delivery through a focused narrative review. 
2.  Specify the algorithm's data structures, state transitions, client -server messages, 
assumptions, and correctness properties. 
3.  Implement the proposed algorithm and a safe direct -replay baseline in the same small 
PWA prototype. 
4.  Compare integrity, communication cost, and completion time under a fixed set of 
failure scenarios. \nPAGE 8\n

1.6 Research Questions and Hypotheses 
RQ1. What established database and synchronization mechanisms can support 
recovery from uncertain delivery in the selected offline-first workflow? 
RQ2. How can a receipt -aware retry algorithm preserve pending operations, 
prevent duplicate logical inserts, and recover after an application restart? 
RQ3. Compared with safe direct replay, under which tested conditions does 
receipt checking reduce application traffic, and what additional requests or delay does it 
introduce? 
H1. Under the stated storage and execution assumptions, both algorithms will 
preserve locally committed valid operations and create at most one server entry per 
operation identifier in all tested scenarios. 
H2. After a lost acknowledgement, receipt checking will reduce retransmitted 
application bytes when the avoided record exchange is larger than the receipt exchange. 
When a request was lost before commit, receipt checking will add communication 
overhead. 
H1 is an acceptance hypothesis to be challenged by fault injection; H2 is a 
conditional performance hypothesis. Neither represents a result already obtained. 
1.7 Significance of the Study 
The practical value is a clearer recovery decision for a common failure: the client 
does not know whether its previous request succeeded. Developers will be able to inspect 
the algorithm, reproduce its failure cases, and decide whether the receipt endpoint is 
worthwhile for their own record sizes and operating conditions. For the thesis, this creates 
a direct connection between database transactions, application state management, and 
measured software behavior.

The working name receipt-aware retry (RAR)  identifies the proposed variant in 
this study. It does not imply that the underlying patterns are previously unknown. 
1.9 Scope and Delimitations 
The study includes one browser profile, one foreground synchronization worker, 
one append -only site -log record type, one local database, and one server database. 
Records will contain a synthetic site code, observation time, activity description, and 
optional quantity and unit. Attachments, edits to existing records, deletion, multi -user 
conflict resolution, and synchronization between several devices are outside the 
implementation scope. 
Testing will cover application restarts and controlled request or response loss. It 
will not establish resistance to device destruction, power failure, user -cleared storage, or 
browser eviction. Local data will be retained in a normal browser profile throughout each 
run. Synchronization resumes when the application is open; background execution while 
the application is closed is not required.

CHAPTER 2: LITERATURE REVIEW 
2.1 Offline Work and Local Persistence 
Kleppmann and colleagues describe local -first software as an approach that gives 
people continued access to their data and supports work without continuous connectivity 
[1]. This provides a motivation for the present study, but does not resolve the mechanics 
of a lost acknowledgement. The proposed work narrows the focus to one record's journey 
from a browser database to a server. 
IndexedDB supports transactional changes to local structured data [2]. In the 
prototype, the record and its outbox item will therefore be written together. The interface 
will report a local save only after that transaction completes. Service -worker caching will 
supply the application assets needed to reopen the interface offline [3]. Browser storage 
has quotas and eviction behavior, so successful restart tests cannot establish indefinite 
preservation [7]. 
2.2 Transactional Outboxes and Duplicate Processing 
The transactional-outbox pattern addresses the gap between committing business 
data and arranging for its later transmission. Its sender stores the business change and an 
outgoing message together, then a separate process delivers the message. A relay can 
transmit more than once if it fails before recording completion [5]. This is relevant to the 
browser because sending a request and updating local status are also separate events. 
The server therefore needs a defined response to retries. Featonby explains the use 
of client request identifiers to make repeated API requests safe, including the case where 
the same identifier is reused with a different intent [4]. The proposed endpoint will 
enforce a unique operation ID and compare immutable content before returning a prior 
result. This moves duplicate prevention into the database transaction rather than relying 
on the client to send only once. 
2.3 Selective Synchronization and Receipt Checking 
CouchDB's replication protocol identifies missing document revisions before 
transferring their bodies [6]. This is relevant prior art for asking what a receiver already 
has. The proposed algorithm uses a narrower idea: it checks a receipt only when a 
previous submission has an uncertain outcome. New operations are sent directly, and the 
prototype does not implement CouchDB's revision trees, peer replication, or conflict 
handling. \nPAGE 11\n 
MS Thesis Proposal | Faculty of Computer Science, 
Kabul University 
Page 6 
This comparison shapes the research claim. The study will investigate a small 
adaptation for immutable browser records and measure its costs. Receipt checking 
introduces another request and server lookup. Its value depends on whether that work 
avoids a larger retransmission and whether the extra round trip matters to the user. 
2.4 Retry Timing and Recovery 
Timeouts indicate that the client did not receive a response in time; they do not 
prove that the server failed to act. Backoff and jitter help control repeated attempts, but 
must be chosen alongside the operation's side effects [8]. Both experimental variants will 
use the same timing policy so that differences can be attributed to receipt checking. 
Recovery after restart needs an equally explicit rule. A stored IN_FLIGHT state 
will be treated as UNCERTAIN when the application reopens. The system will retain its 
operation ID and content. It will not turn an unfinished request into a new business 
operation or silently remove it after a fixed number of retries.

CHAPTER 3: RESEARCH METHODOLOGY 
3.1 Research Approach 
The study will follow a design science approach: define a practical problem, 
specify an artifact, implement it, and evaluate it against stated objectives [9]. The artifact 
is the synchronization algorithm, with the PWA serving as its experimental 
implementation. A narrative review will inform the design, followed by controlled 
experiments and correctness reasoning. 
3.2 Study Context and Environment 
NBCC supplies the motivating construction context. The experiment itself will 
use generated records and run on an existing workstation with one Chromium -based 
browser, IndexedDB, a JavaScript client, and a small HTTP service backed by SQLite. 
SQLite is sufficient for the single -server experiment; no database -product comparison is 
planned. Versions, operating system, schema, runtime settings, and source revision will 
be recorded before data collection. 
The service worker will be installed and the application opened once before 
offline trials. A test transport will inject failures at named boundaries, such as before 
server processing or after a committed transaction. This produces repeatable cases 
without requiring a physical network laboratory. Timing results will describe this 
controlled setup, not network performance across Afghanistan. 
3.3 Focused Narrative Literature Review 
The review will explain how selected sources inform the design and where their 
assumptions differ. It will follow an explicit search and selection rationale, consistent 
with guidance on choosing review methods to fit the research question [10]. Searches will 
target local -first software, browser persistence, transactional outboxes, idempotency, 
uncertain delivery, selective synchronization, and retry recovery. 
Google Scholar and accessible publisher or university repositories will be used for 
research papers. Official specifications, project documentation, and original technical 
articles will supply implementation details. A source log will record the query, access 
date, bibliographic information, evidence type, relevant mechanism, and reason for 
inclusion. Backward references from central papers will be followed where relevant. 
Sources that only advertise offline support without explaining a mechanism will not 
substantiate algorithmic claims. \nPAGE 13\n

3.5 Proposed Receipt Aware Retry Algorithm 
The algorithm has two paths. A new pending operation is submitted directly. An 
operation whose earlier outcome is uncertain first requests a receipt using its ID and 
digest. A matching committed receipt completes the operation locally; an absent receipt 
leads to resubmission; a content mismatch stops automatic processing and preserves the 
entry for inspection. 
3.5.1 Client States and Recovery 
State Meaning and next action 
PENDING Saved locally and eligible for first submission. 
IN_FLIGHT Persisted immediately before submitting the full payload. 
UNCERTAIN Response was lost, transient failure occurred, or an IN_FLIGHT item survived restart. 
ACKNOWLEDGED A matching committed receipt was verified and saved locally. 
BLOCKED Permanent validation or identity error; retain record and display reason.

Only one foreground worker will process the queue. After restart it will change 
remaining IN_FLIGHT items to UNCERTAIN. A failed receipt lookup leaves the item 
uncertain. A successful ABSENT response permits a direct submission during the same 
attempt; it does not authorize deletion. Later due items may proceed after a failed item is 
rescheduled, avoiding indefinite blockage of the queue.

3.5.2 Algorithm Pseudocode 
The following procedures define the proposed behavior. A local state transition 
must commit before the next network action. Transient failures include timeouts and 
unavailable service responses; malformed responses are never treated as successful 
receipts.

  id = new UUID; bytes = canonical_encode(payload)  
  digest = SHA256(bytes)  
  in one local transaction:  
    insert site_log(id, bytes, digest)  
    insert outbox(id, sequence, PENDING, retry_count=0)  
  report local save only after transaction completes

  transactionally change IN_FLIGHT items to UNCERTAIN  
  while application is running:  
    select the next due PENDING or UNCERTAIN item

    if MISMATCH: mark BLOCKED with reason; return  
    if reply is not valid ABSENT: reschedule UNCERTAIN; return  
  persist IN_FLIGHT before network dispatch  
  reply = SUBMIT(item.id, item.bytes, item.digest)  
  if matching COMMITTED receipt: mark ACKNOWLEDGED  
  else if permanent validation or identity error: mark BLOCKED  
  else: reschedule UNCERTAIN with the same id and payload 
SERVER_SUBMIT(id, bytes, digest)  
  validate schema and recomputed digest  
  begin database write transaction  
    if id already exists:  
      if stored bytes differ: roll back; return MISMATCH  
      else: read the stored receipt  
    otherwise: 
      insert site_log(id, bytes)  
      insert receipt(id, digest, COMMITTED)  
  commit transaction before returning the receipt  
 
SERVER_LOOKUP(id, digest)  
  read committed receipt from authoritative database  
  if absent: return ABSENT  
  if stored digest differs: return MISMATCH  
  return COMMITTED(id, digest, stored_result) 
The server transaction will serialize the existence check and insertion, with a 
unique key as a second safeguard. An ABSENT reply can race with an earlier delayed 
submission. Safety still comes from the unique ID and immutable payload check when 
either request reaches the server. 
If any local state transaction fails, the worker will pause and retain the record. 
Once storage is usable, it will run restart recovery before selecting further work. This 
includes failure to persist an acknowledgement: the interface will report synchronization 
complete only after that local transaction commits. Local storage errors will be logged 
separately from network errors. 
Transient failures will use capped exponential backoff with jitter: a one -second 
initial ceiling, doubling to a maximum of 30 seconds. These are proposed experimental 
settings, to be frozen after the pilot. The cap limits the waiting interval, not the number of 
times an operation may be retained or retried. Authentication expiry will pause 
synchronization for recovery rather than acknowledge or delete data. \nPAGE 17\n

3.5.3 Lost Acknowledgement Example 
Suppose the server commits operation A17 but its response is dropped. The client 
retains A17 as uncertain. At the next attempt, it asks for the receipt for A17. If the 
returned digest matches, it marks the operation acknowledged without sending the 
activity description again. If the original request never committed, the receipt is absent 
and the full record must still be sent. This second case explains the algorithm's extra cost. 
Figure 3. Recovery after a committed operation loses its acknowledgement. 
 
3.6 Correctness Properties and Assumptions 
Local retention:  once SAVE reports success, the record and outbox item exist 
together. Retry handling keeps the record until an acknowledged or explicitly blocked 
state is recorded. This property assumes that browser storage remains intact and local 
transaction completion is respected. 
At-most-once logical insertion:  for a given operation ID, the unique server key 
permits one entry. Repeated submissions return the same committed receipt when content 
matches. Different content under the same ID is rejected. Repeated messages can still 
cross the network; the claim concerns the database effect. 
\nPAGE 18\n 
MS Thesis Proposal | Faculty of Computer Science, 
Kabul University 
Page 13 
Sound acknowledgement:  the server exposes a receipt only after the entry and 
receipt transaction commits. The client checks the ID and digest before acknowledging 
locally. Hash collision resistance and correct implementation are assumed; exact payload 
comparison protects duplicate submissions with conflicting content. 
Eventual completion:  a valid queued operation can complete if the application 
continues to run, retries are scheduled fairly, storage and credentials remain available, and 
the server and connection eventually allow successful exchanges. Permanent 
disconnection cannot satisfy this condition. A finite test can expose counterexamples but 
cannot prove liveness for every execution. 
Correctness will be assessed through state -transition reasoning and the test 
scenarios. The specification will also account for transaction aborts: a failed local save 
must not be shown as saved, and a failed server commit must not produce a committed 
receipt. 
3.7 Baseline and Controlled Comparison 
The principal baseline is safe direct replay . It uses the same local transaction, 
stable operation ID, immutable payload, server transaction, unique keys, backoff, and 
restart recovery. For an uncertain operation it directly resends the full payload instead of 
looking up a receipt. This isolates the decision being studied while keeping both 
implementations safe by design. 
A server -dependent form is not the primary comparator because its inability to 
save offline would not establish the value of receipt checking. Both variants will use one 
outstanding operation at a time and the same dataset and failure locations. No variant will 
receive a different retry budget, storage mechanism, or server capacity.

The harness will sum the UTF -8 body bytes of every issued request and every 
generated server response, each counted once, including deliberately dropped messages. 
A request dropped before processing generates no response to count. This measures 
attempted application exchange work rather than bytes successfully delivered. It excludes 
HTTP headers, TLS, TCP retransmissions, and radio energy; it is not an estimate of a 
mobile user's bill. 
Integrity criteria are zero missing valid records, zero duplicate logical effects, 
matching final payloads, and retention of blocked records with an explanation. A run that 
exceeds the recovery window will be reported as incomplete; it will not be assigned an 
invented completion time. Communication savings will be reported alongside any extra 
requests or latency. 
3.10 Analysis and Interpretation 
For each condition, the analysis will report counts, medians, ranges, and paired 
differences between algorithms. The comparison will include every main run, with 
failures and reruns identified. The pilot may refine operational settings, but those settings 
and workload seeds will be fixed before the main experiment. 
A simple cost model will guide interpretation. Let R be the application bytes for a 
receipt request and response, P the bytes for replaying a record and receiving its 
acknowledgement, and q the fraction of uncertain operations already committed. 
Expected recovery traffic is R + (1 − q)P for receipt checking and P for direct replay. 
Under this simplified model, receipt checking saves bytes when qP > R. This assumes 
equal-sized committed and absent receipt exchanges, successful recovery exchanges, and 
no transport headers. Actual receipt sizes will be measured separately, and the analysis 
will use their observed costs when they differ. The model predicts no universal latency 
advantage. 
3.11 Validity and Limitations 
The experiment isolates specific failure boundaries, which improves 
reproducibility but does not reproduce every pattern of mobile connectivity. One browser, 
one server, fixed payload sizes, and synthetic records limit generalization. Normal 
application restart is different from an operating -system crash or physical storage failure. 
Timing on one workstation is also sensitive to competing processes, so run order and 
environment will be recorded. \nPAGE 21\n

Both variants will share code for persistence, validation, and server writes. Only 
uncertain-delivery handling will differ. This reduces implementation imbalance. A source 
review may show that the proposed variation closely matches existing work; in that case 
the thesis contribution will be its explicit adaptation and evaluation within this scope. 
3.12 Ethics and Data Management 
The study requires no interviews or identifiable staff information. All records will 
be synthetic and the prototype will be isolated from the NBCC production MIS. Logs will 
contain test IDs, sizes, states, and timings. Source code, a schema, workload generator, 
seeds, and sanitized results will accompany the thesis where university rules permit. 
3.13 Expected Outputs 
The study will deliver a focused narrative review, the RAR algorithm and its 
stated properties, a prototype with two selectable policies, and a reproducible evaluation 
report. Conclusions will identify the conditions in which receipt checking is worthwhile

APPENDIX B: DEFENSE EXPLANATION 
The proposed study asks what an offline application should do when it cannot tell 
whether a record reached the server. Both algorithms keep the record locally and prevent 
duplicate inserts. The proposed variant first checks a small server receipt, while the 
baseline resends the record. The experiment will determine whether the avoided 
retransmission is worth the extra check. 
The underlying database patterns are established. The thesis contribution will be a 
precise algorithmic adaptation, a clearly bounded implementation, and evidence about its 
communication tradeoff. Its usefulness will be judged by correctness and measured 
behavior, including cases where receipt checking performs worse.
